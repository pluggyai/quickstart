# Prompt: receive and verify Pluggy webhooks

> Paste this into your coding agent, inside the repository of the backend that will receive Pluggy notifications.

## Goal

Add an HTTPS endpoint that receives Pluggy webhooks, accepts only notifications that really come from Pluggy, and turns each one into an idempotent job that re-reads the data from the Pluggy API.

## Prerequisites

- Server-side Pluggy client from [`backend-connect-token.md`](backend-connect-token.md) (credentials in the environment, cached API key).
- A table that maps `item_id` → `user_id` (created there, or ask).
- Configuration:
  - `PLUGGY_WEBHOOK_SECRET` (required): the application's **signing secret** (`whsec_…`), generated by the team Owner in the Dashboard under the application's **Webhooks** → *Generate signing secret*.
  - `PLUGGY_WEBHOOK_SECRET_PREVIOUS` (optional): the old secret during a rotation.
  - `PLUGGY_CLIENT_ID` (already present) to check `clientId`.

## Before you write code

- If the Pluggy agent skills or the docs MCP server (`https://mcp.pluggy.ai/mcp`) are available, use them to confirm the event list and payloads.
- Inspect the project and tell me: framework, how to read the **raw request body** in it (many frameworks parse JSON before your handler runs), whether there is a job queue / background worker, and where processed event ids could be stored. Ask before adding infrastructure.

## Contract

Docs: [Webhook reference](https://docs.pluggy.ai/en/docs/reference/webhooks) (events, payload, delivery and retries), [Webhook security](https://docs.pluggy.ai/en/docs/developer-tools/webhook-security), [Configure and troubleshoot](https://docs.pluggy.ai/en/docs/developer-tools/webhook-troubleshoot), [Two-way sync with webhooks](https://docs.pluggy.ai/en/docs/integration-checklist/webhooks-sync).

- Subscription: a webhook created in the Dashboard (or `POST /webhooks` if the team has API management enabled), and/or `webhookUrl` on the Connect Token. The URL must be public HTTPS on port 443.
- Signature header: `X-Pluggy-Signature: t=<unix seconds>,v1=<hex>`. `v1` is the lowercase hex **HMAC-SHA256** of the string `<t>.<raw body>` keyed with the full secret (including `whsec_`). Reject when the header is missing or malformed, when `t` is more than **5 minutes** from now, or when no accepted secret matches (constant-time comparison). The webhook-security page has reference implementations in several languages.
- Payload: `event`, `eventId`, `clientId`, `triggeredBy`, and the entity id (`itemId`, `accountId`, `transactionIds`, …). `clientUserId` is present on `item/*` events only.
- Responses: answer `2xx` quickly (Pluggy counts more than 10 seconds as a failure and retries); `401` for a request that fails verification (not retried); `5xx` for a temporary problem on your side (retried).

## What to build

1. `POST /pluggy/webhooks` (or the project's naming) that:
   - reads the raw body, verifies the signature against `[PLUGGY_WEBHOOK_SECRET, PLUGGY_WEBHOOK_SECRET_PREVIOUS]`, and answers `401` before parsing JSON if it fails;
   - answers `503` and logs a configuration error if no secret is configured (fail closed);
   - ignores (with `2xx`) a payload whose `clientId` is not `PLUGGY_CLIENT_ID`, an `event` it does not handle, or a payload missing the fields it needs;
   - validates ids as UUIDs;
   - de-duplicates on `eventId`, then enqueues (or, without a queue, processes within the time budget) and answers `2xx`.
2. Handlers that **re-fetch** from the API with the server's own API key instead of trusting the payload:
   - `item/created`, `item/updated`, `item/login_succeeded`, `item/error`, `item/waiting_user_input`, `item/waiting_user_action`: `GET /items/{itemId}`, store status and `clientUserId` as the owner. Only bind an item to a user from the API response, never from the payload alone.
   - `item/deleted`: delete the item and its data locally.
   - `transactions/created`: page `createdTransactionsLink` exactly as received (cursor pagination, follow `next` until `null`).
   - `transactions/updated`: `GET /v2/transactions?accountId=…&ids=…`.
   - `transactions/deleted`: delete those ids locally.
   - Data sync details are in [`sync-financial-data.md`](sync-financial-data.md); implement only the dispatch here if that prompt has not been run.

## Security requirements

- The signing secret lives in the secret store, never in source or logs.
- Never log the raw body, headers (they may carry the secret header) or full payloads; log `event`, `eventId` and ids.
- Verification happens before any database write or API call.
- If the team also configured a secret `Authorization` header on a Dashboard webhook, you may require it in addition, but the signature is the check that covers `webhookUrl` deliveries too.

## Acceptance checks (run them and report the results)

Write automated tests that sign bodies with a test secret, and run them:

- [ ] No `X-Pluggy-Signature` → `401`, handler not called.
- [ ] Wrong signature → `401`; signature with `t` 10 minutes old → `401`; body changed after signing → `401`.
- [ ] Valid signature with the previous secret → accepted.
- [ ] No secret configured → `503`.
- [ ] Valid signature, foreign `clientId` → `2xx`, no processing.
- [ ] The same `eventId` twice → processed once, both answered `2xx`.
- [ ] `item/updated` triggers `GET /items/{id}` (mocked) and stores `clientUserId` from the API response, not from the payload.
- [ ] Tests and logs contain no secret value.
- [ ] Linter, type checker and existing tests pass.

## Adapt to the user's stack

Use the project's queue if it has one (SQS, Pub/Sub, BullMQ, Sidekiq, Celery…). On serverless platforms without a queue, process inline but keep within the 10-second budget, and make the handlers idempotent so retries are harmless. To test locally, expose the endpoint through an HTTPS tunnel and register that URL; `localhost` is rejected.
